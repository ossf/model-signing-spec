# OMS Closure Predicate

**Version:** 0.1 (Draft)

## 1. Introduction

An OMS signature ([OMS v1.0][oms]) covers the files in a model
directory. While loading a model, a loader can fetch further files by
name from other sources: custom code from another repository, the
configuration or weights of a base model, or a compiled kernel. These
files are not in the OMS manifest. This means that a model whose 
signature verifies can still load content that is not covered by the 
signature.

This document defines an optional predicate for this case. The
producer of a model lists the files, which the loader fetches from 
outside the model directory. The producer signs this list as a 
separate in-toto statement and binds the statement to the model's OMS
manifest. Subsequently, a consumer can check each file when the
loader fetches it.

The closure predicate is separate from the OMS predicate. It does not
change `https://model_signing/signature/v1.0`, its schema, or the
verification of OMS bundles. A verifier, which does not implement this
specification, is not affected by it.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in [RFC 2119][rfc-2119].

### 1.1. Scope

This version defines:

1. The predicate type, subject and predicate body of a closure
   statement.
2. The manifest digest, which binds a closure statement to an
   OMS-signed model.
3. How a consumer verifies a closure statement, its binding to a model,
   and the files the loader fetches.

Out of scope for this version:

- Authorization. Which dependencies a consumer accepts, and from which
  signers, is consumer policy (see
  [Section 7.1](#71-declared-is-not-authorized)).
- How a loader exposes its fetches to a verifier.
- The file name and location of the closure bundle (see
  [sigstore/model-transparency#587][mt-587]).
- Models signed with the deprecated `https://model_signing/Digests/v0.1`
  predicate.

## 2. Terminology

The terms defined in [OMS v1.0][oms] Section 3 apply.

**Dependency**: The files a loader fetches from one source outside the
model directory while loading the model, for example from another
model repository.

**Closure**: All dependencies of a model, including dependencies of
dependencies.

**Closure statement**: An [in-toto Statement v1][intoto-statement] with
the predicate type defined in [Section 3.1](#31-predicate-type).

**Closure bundle**: A Sigstore bundle whose DSSE envelope carries a
closure statement.

**Producer**: The party that creates and signs a closure statement,
normally the publisher of the model.

**Consumer**: The party that loads the model and verifies the closure
statement.

**Fetch**: The retrieval of one file of a dependency by the loader,
identified by the dependency's URI and the file's path within it.

## 3. Closure Statement

### 3.1. Predicate Type

```
https://model_signing/closure/v0.1
```

Producers MUST set `predicateType` to exactly this URI. Like the OMS
predicate type ([OMS v1.0][oms] Section 5.1), it is an identifier and
does not resolve. The version follows 
[`VERSIONING.md`](../../VERSIONING.md). This document is a
Draft. A new version MAY contain breaking changes.

### 3.2. Subject

`subject` MUST contain exactly one entry, the model the closure belongs
to:

| Field | Value |
|---|---|
| `name` | The model name. Producers SHOULD use `subject[0].name` of the model's OMS statement. Informational only. |
| `digest` | A DigestSet with exactly one key, `omsManifest`, whose value is the manifest digest of the model ([Section 4](#4-manifest-digest)) as lowercase hex. |

The subject MUST NOT carry the OMS root digest ([OMS v1.0][oms]
Section 6.5.1) or any other digest. in-toto treats two DigestSets as
matching if one accepted key matches ([DigestSet][intoto-digest-set]).
A second key would allow a consumer match the statement to a model for
which is was not created for (see
[Section 7.2](#72-why-the-subject-is-not-the-oms-root-digest)).

### 3.3. Predicate Body

```json
{
  "dependencies": [ ... ]
}
```

`dependencies` is REQUIRED and lists the whole closure, flattened: 
a dependency of a dependency is an entry of its own. An empty array
declares that the loader fetches nothing from outside the model
directory.

Each entry has these fields:

| Field | Type | Required | Description |
|---|---|---|---|
| `uri` | string | REQUIRED | The source from which the loader fetches the dependency ([Section 3.3.1](#331-uri)). |
| `kind` | string | REQUIRED | What the loader does with the dependency ([Section 3.3.2](#332-kind)). |
| `resources` | array | REQUIRED | The files of the dependency ([Section 3.3.3](#333-resources)). |
| `claimed_signer` | object | OPTIONAL | The identity the producer expects to have signed the dependency ([Section 3.3.4](#334-claimed_signer)). |

Two entries MUST NOT have the same `uri`.

#### 3.3.1. `uri`

A URI that identifies the source. Consumers compare `uri` values byte
for byte, without normalization.

For a repository on the Hugging Face Hub, `uri` MUST be
`https://huggingface.co/<repo_id>`, where `<repo_id>` is the repository
id as the loader resolves it, for example
`https://huggingface.co/example-org/custom-layers`. This version does
not define URIs for other sources. For those, producers MUST use a URI
that clearly identifies the source.

#### 3.3.2. `kind`

| Value | Meaning |
|---|---|
| `code` | Source files the loader imports or executes, including model, configuration, tokenizer and processor classes. |
| `model` | Files of another model that the loader reads, such as a base model's configuration or weights. |
| `kernel` | Compiled code the loader loads, such as a kernel library. |

`kind` does not change verification in this version. It allows
consumer policy to treat code and data differently.

#### 3.3.3. `resources`

The files of the dependency, as resource descriptors with the fields
of OMS resources ([OMS v1.0][oms] Section 5.2.1): `name`, `digest` and
`algorithm`.

- `name` is the path of the file relative to the root of the
  dependency, canonicalized per [OMS v1.0][oms] Section 6.1.2.
- `digest` covers the whole file ([OMS v1.0][oms] Section 6.3.1).
- `algorithm` MUST be an identifier from the
  [algorithm registry](../../algorithm-registry.md).

`resources` MUST contain at least one entry and MUST NOT contain two
entries with the same `name`.

A fetched file that `resources` does not list fails the fetch check
([Section 6.3](#63-fetch-check)), so an incomplete list fails closed.
Producers SHOULD list every file of a `code` or `kernel` dependency,
since code can import or read files other than the one the loader was
asked for.

#### 3.3.4. `claimed_signer`

The identity the producer expects to have signed the dependency. It is
an assertion by the producer, not a trust root (see
[Section 7.1](#71-declared-is-not-authorized)).

`method` is REQUIRED and selects the remaining fields, following the
signing methods of [OMS v1.0][oms] Section 4.1:

| `method` | Fields | Meaning |
|---|---|---|
| `key` | `public_key_sha256` | SHA-256 of the DER-encoded SubjectPublicKeyInfo of the signing key, lowercase hex. |
| `certificate` | `root_certificate_sha256` | SHA-256 of the DER-encoded root certificate that the signing chain validates to, lowercase hex. |
| `sigstore` | `identity`, `issuer` | The Subject Alternative Name of the signing certificate and the OIDC issuer recorded in it. Both are REQUIRED. The identity alone does not identify a signer. |

### 3.4. Parsing Rules

This predicate follows the in-toto [parsing rules][intoto-parsing].
Consumers MUST ignore fields that this version does not define in the
predicate body, in dependency entries and in `claimed_signer`. A field 
will only be introduced with a new predicate type version, if its 
omission would allow a consumer to accept a fetch that they would
otherwise be refused.

`kind` and `method` values that this version does not define MUST be
rejected.

A consumer MUST reject a closure statement that violates a requirement
of this section, including duplicate `uri` values within `dependencies`
and duplicate `name` values within a dependency's `resources`. The
JSON Schema ([Section 9](#9-schemas-and-test-vectors)) cannot express
these two rules.

### 3.5. Example

A model whose custom code comes from another repository, and whose
code fetches a base model's configuration when it runs:

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "model",
      "digest": {
        "omsManifest": "0eda4ca6013c2bda4e02bd8e3260fc6e54c7e48edcc13736f209c5f3a030d273"
      }
    }
  ],
  "predicateType": "https://model_signing/closure/v0.1",
  "predicate": {
    "dependencies": [
      {
        "uri": "https://huggingface.co/example-org/base-encoder",
        "kind": "model",
        "resources": [
          {
            "name": "config.json",
            "algorithm": "sha256",
            "digest": "3bce584347100ee3296036135fb3022fee2a387a08e9a5a36cdf2db96e21984a"
          }
        ]
      },
      {
        "uri": "https://huggingface.co/example-org/custom-layers",
        "kind": "code",
        "resources": [
          {
            "name": "configuration_example.py",
            "algorithm": "sha256",
            "digest": "2e3bfebb0371712a911dc18a90039e0df9bf4cdd28a414d285037d642b61da7c"
          },
          {
            "name": "modeling_example.py",
            "algorithm": "sha256",
            "digest": "07981daf22907fb970e7ff6fb1aa0bfc9287d1a7eddedd1a58befa0301183006"
          }
        ],
        "claimed_signer": {
          "method": "sigstore",
          "identity": "https://github.com/example-org/custom-layers/.github/workflows/release.yml@refs/heads/main",
          "issuer": "https://token.actions.githubusercontent.com"
        }
      }
    ]
  }
}
```

This is the test vector
[`valid/code-and-model.json`](../../test-vectors/closure/v0.1/valid/code-and-model.json).

## 4. Manifest Digest

The manifest digest identifies an OMS-signed model by its file names,
algorithms and digests. It is computed from the `resources` array of
the model's verified OMS statement ([OMS v1.0][oms] Section 5.2.1):

1. Order the resource descriptors by `name` in Unicode code point order
   (the same as the byte order of their UTF-8 encoding). If two
   descriptors have the same `name`, reject the list.
2. Start with the ASCII string `oms-manifest/v1` followed by one zero
   byte (16 bytes in total).
3. For each descriptor in order, append
   `len(name) || name || len(algorithm) || algorithm || len(digest) || digest`,
   where `name` and `algorithm` are UTF-8 encoded, `digest` is the raw
   bytes decoded from the hex string, and `len(x)` is the length of `x`
   in bytes as an unsigned 64-bit big-endian integer.
4. Compute SHA-256 over the result and encode it as lowercase hex.

Shard resources ([OMS v1.0][oms] Section 6.3.2) are included like any
other resource, under their `path:start:end` names.

Unlike the root digest ([OMS v1.0][oms] Section 6.5.1), the manifest
digest covers the names. Two models that hold the same file contents
under different names can have the same root digest, but have different
manifest digests.

## 5. Producing a Closure Statement

1. Sign the model per [OMS v1.0][oms] and compute the manifest digest
   from the `resources` of its OMS statement.
2. Determine the closure. Producers SHOULD do this by loading the model
   with the loader it targets and recording every fetch, since code can
   fetch further dependencies when it runs and reading configuration
   files alone misses these.
3. For each dependency, record its `uri`, `kind` and `resources`, and
   optionally its `claimed_signer`.
4. Assemble the closure statement per [Section 3](#3-closure-statement).
5. Sign it and wrap it in a Sigstore bundle as for an OMS bundle
   ([OMS v1.0][oms] Sections 4.1, 6.7 and 6.8). The closure bundle MUST
   validate against
   [`schemas/v1.0/bundle.schema.json`](../../schemas/v1.0/bundle.schema.json).

Producers SHOULD sign the closure statement with the same identity as
the model's OMS bundle.

Producers SHOULD store the closure bundle next to the model's OMS
bundle. If it is stored inside the model directory, its path MUST be
excluded from the model's signing scope ([OMS v1.0][oms] Section 6.2);
otherwise verification of the model fails ([OMS v1.0][oms]
Section 8.5).

## 6. Verification

A consumer performs three checks and reports their results separately.
Passing one check says nothing about the others.

### 6.1. Statement Verification

1. Verify the closure bundle as an OMS bundle ([OMS v1.0][oms]
   Sections 8.1 and 8.2).
2. Check that the consumer's policy accepts the signer of the closure
   bundle for this model. A common policy accepts the signer it already
   accepts for the model's OMS bundle.
3. Validate the decoded statement against
   [`schemas/closure/v0.1/statement.schema.json`](../../schemas/closure/v0.1/statement.schema.json)
   and the rules of [Section 3](#3-closure-statement).

The result is `verified` if all steps succeed, otherwise `failed`.

### 6.2. Model Binding

1. Verify the model's OMS bundle per [OMS v1.0][oms] Section 8.
2. Compute the manifest digest from the `resources` of the verified OMS
   statement ([Section 4](#4-manifest-digest)).
3. Compare it with `subject[0].digest.omsManifest` of the closure
   statement.

The result is `established` if the model's OMS bundle verifies and the
two digests are equal, otherwise `not established`. A consumer MUST NOT
use a closure statement as the closure of a model unless the binding is
`established`.

### 6.3. Fetch Check

For each file that the loader fetches from outside the model directory:

1. Find the dependency whose `uri` equals the source of the fetch. If
   there is none, the result is `undeclared`.
2. In that dependency, find the resource whose `name` equals the path of
   the file. If there is none, the result is `undeclared`.
3. Compute the digest of the fetched bytes with the resource's
   `algorithm`. If it differs from the resource's `digest`, the result
   is `mismatch`, otherwise `match`.

The digest MUST be computed over the bytes the loader uses, not over a
separate download.

A consumer that requires closure coverage MUST NOT let the loader use a
fetched file unless the statement is `verified`, the binding is
`established`, and the result for that file is `match`.

`match` means only that the file is the one the producer declared.
Whether the consumer trusts that file is a policy decision (see
[Section 7.1](#71-declared-is-not-authorized)).

## 7. Security Considerations

### 7.1. Declared Is Not Authorized

A closure statement records what the producer says the loader fetches.
A producer can declare any dependency, including a hostile one. 
Consequently, every fetch of te dependency results in `match`. 
Therefore, a closure statement does not tell a consumer which
dependencies to trust. Consumers authorize dependencies in their own 
policy, either by digest or by a signer identity they trust for that 
dependency. A declared closure is a reasonable starting point for 
writing such a policy.

The same applies to `claimed_signer`. A consumer MUST NOT accept a
dependency because it is signed by its claimed signer unless the
consumer's policy authorizes that signer for that dependency. A
consumer MAY use `claimed_signer` to locate and verify the dependency's
own signature, and to detect that the actual signer differs from the
claimed one.

### 7.2. Why the Subject Is Not the OMS Root Digest

The OMS root digest is computed over the resource digests in name
order, but not over the names. Consider two models that hold the same
two files. In model A, the file named `config.json` refers to code in
repository X. In model B, the files are renamed so that `config.json`
is the file that refers to repository Y. The digests
appear in the same name order. Therefore, both models have the same root
digest, but a loader that reads `config.json` fetches different code.
A closure statement bound to the root digest would apply to both
models. The manifest digest covers the names, so it applies to one.

The test vectors include this pair
([`manifest-digest.json`](../../test-vectors/closure/v0.1/manifest-digest.json),
[`binding.json`](../../test-vectors/closure/v0.1/binding.json)).

### 7.3. Missing Statements

A closure bundle is a detached file and can be withheld or removed, like
any other attestation. A consumer that requires closure coverage MUST
treat a missing closure statement as a failure. A consumer that does
not require it loads the model as it would without this predicate.

### 7.4. Coverage

The fetch check only sees fetches that pass through the point where the
consumer hooks into the loader. Files that code downloads by other
means are not checked.

Files excluded from the model's OMS signing scope ([OMS v1.0][oms]
Section 6.2) are not covered by the model's signature, and a closure
statement does not cover them either.

## 8. Conformance

A producer conforms to this specification if it produces closure
statements per [Section 3](#3-closure-statement), computes the subject
per [Section 4](#4-manifest-digest) and produces closure bundles per
[Section 5](#5-producing-a-closure-statement).

A verifier conforms to this specification if it implements
[Section 4](#4-manifest-digest) and
[Section 6](#6-verification), and reports the three results of
[Section 6](#6-verification) separately.
